# M5 · 창고 반복 운송과 고장 복구

**2026-11-28 현재 M5 진행 중.** M4 후보 3개의 입력 재생과 명령 전환 회귀시험을 마쳤다. M5 종료 판단에는 같은 후보가 새 Gazebo 주행에서 수행한 반복 운송, 고장 복구, 두 로봇의 독립 제어와 fleet 대기·재개 기록이 필요하다.

## 확인한 결과

M3의 직렬 shadow·learned 주행 원본과 rosbag 해시를 검산하고 유효한 정책 관측 381개를 오차 없이 재구성했다. 정책이 동작했던 344개 시점의 입력을 M4 학습 seed 7·19·31에 각각 전달했다. 총 1,032회에서 NumPy의 재실행 출력이 모두 일치했고 SB3와의 최대 절대차는 4.18×10⁻⁷ 미만이었다. 로컬 단일 스레드 CPU에서 NumPy 추론 최댓값은 0.059ms 미만이었으며 25ms 초과는 0회였다. 이 시간은 고정된 입력의 추론 구간에 한정한다. 새 정책이 만들어낼 궤적과 Gazebo 부하에 따른 제어 주기는 폐루프 시험에서 측정한다. [후보별 원시 수치](../../experiments/m5/candidate-replay.json)

명령 전환 회귀시험에서는 센서 누락 시 정지, 지연 시 DWA 전환과 learned 복귀, 목표 취소, 현재 목표의 재계획 이후에만 재출발하는 조건을 확인했다. [운용 상태와 고장 주입 방법](operations.md)

기존 fleet 관리자 코드에 정해진 두 로봇의 위치·속도를 입력한 12초 재생에서도 목표 교체를 확인했다. 관리자는 뒤쪽 `amr2`에만 3.4초에 대기 위치를 발행했고, 앞쪽 로봇이 이동한 뒤 7.2초에 원래 목표를 다시 발행했다. 실제 센서와 주행기의 반응은 아래 `fleet` 시험에서 측정한다. [관리자 발행 이력](../../experiments/m5/fleet-manager-replay.json)

## Gazebo 시험과 판정

| 실행 묶음 | 시행 | 확인할 결과 |
|---|---:|---|
| `paired` | 6 | 후보별 같은 4m 경로를 장애물 없이 한 번, 일시 차단을 넣어 한 번 달린다. 차단 전 이동·정지, 장애물 제거 관측, 제거 후 0.25m 이상 재전진과 무충돌 도착을 기록한다. |
| `sequence` | 3 | 후보별 근거리 목표 세 개를 두 번 반복한다. 새로 발행한 목표마다 기록과 도착 위치를 대조한다. |
| `faults` | 3 | 이동 중 스캔 누락과 추론 지연을 순서대로 주입한다. 정지·DWA 주행·learned 복귀·목표 취소 후 정지·새 목표 도착을 기록한다. |
| `transport` | 3 | 후보별 50m 운송로를 두 번 왕복한다. 네 구간의 도착과 접촉 이력을 각각 판정한다. |
| `pair` | 1 | seed 7을 두 대에 올리고 서로 다른 목표를 준다. 한 대만 정지시켰을 때 다른 로봇의 명령·주행이 유지되는지 확인한다. [두 로봇 시험](pair.md) |
| `fleet` | 1 | 같은 seed로 upstream 교착 관리자를 기동한다. 관리자가 발행한 대기·재개 목표와 각 로봇의 상태·실제 속도·접촉을 대조한다. |

단일 로봇의 도착은 recorder의 `ARRIVED`, 구간 전체에서 유효한 무충돌 계측, learned 제어 이력, Gazebo 실제 위치의 목표 오차 0.25m 이내를 모두 요구한다. 고장 실험의 첫 구간은 명시적인 취소와 실제 정지가 기대 결과다. 차단·취소 후 정지는 최종 명령이 0이고 실제 선속도 0.02m/s 미만, 각속도 0.03rad/s 미만인 상태가 지속될 때 인정한다. 각 seed는 학습된 정책의 식별자다. 개발 시험만 수행하며 독립 시험은 M6에 남긴다.

## 실행과 결과 확인

맥의 Docker Desktop을 켜고 저장소 루트에서 실행한다. M2·M3에서 사용한 CPU 이미지 `opticore-m2-local:humble-fortress`, M2 파일 묶음, M4 후보 번들 3개가 필요하다. 현재 커밋을 새 컨테이너에서 빌드하고 두 접촉 계측 시험을 통과한 다음 주행을 시작한다.

```bash
bash scripts/m5/run_local.sh paired
```

전체 17회는 `bash scripts/m5/run_local.sh all`로 실행한다. 위 표의 이름을 주면 해당 묶음만 실행한다. 위치를 바꾸려면 `M5_PILOT_KIT`에 M2 파일 경로, `M5_RUNS`에 세 후보 디렉터리의 상위 경로를 지정한다. `fleet`와 `all`에는 고정한 `amr_fleet` 패키지도 필요하다. 로컬에 준비된 사본을 사용하거나 `M5_UPSTREAM_REPO`에 `opticore-amr` 체크아웃을 지정할 수 있다. 실행기는 커밋 `e8c9197`에서 해당 패키지를 읽는다.

실행할 때 출력한 `Results` 디렉터리에서 `session.log`로 빌드·기동을, `trials/development/summary.json`으로 시행별 결과를 확인한다. `suite_verdict`는 진행 중 `running`, 전체 통과 `passed`, 측정된 실패 `failed`, 유효한 증거 누락 `invalid`다. 완료 시 종료 코드는 각각 통과 0, 측정된 실패 3, 증거 누락 1이다. 원인 분석을 위해 각 시행의 원시 기록과 실제 시작·종료 시각을 보존한다.

Humble·Fortress가 설치된 리눅스에서는 같은 진입점을 사용할 수 있다. 결과 경로에는 아직 존재하지 않는 디렉터리를 지정한다.

```bash
xvfb-run -a bash scripts/m5/run_on_humble.sh "$UPSTREAM" "$CANDIDATES" "$NEW_RESULTS" paired
```

# M5 · 창고 반복 운송과 고장 복구

**2026-11-28 M5 미통과.** 새 Gazebo 주행에서 계획한 17개 조건을 모두 유효하게 측정했다. 단일 로봇 15회 중 2회(seed 31의 4m 기준 주행·고장 복구), 두 로봇 2회 중 2회(개별 제어·fleet 대기와 재개)가 통과했다. 17회 전체에서 접촉은 0회였다. 세 후보 모두 일시 차단 후 도착, 근거리 반복 운송, 50m 두 번 왕복 기준에 미달해 M6 독립 시험에 올릴 후보를 확정하지 않았다.

실제 주행은 2026-11-28 14:47:04–15:35:27 KST에 로컬 CPU와 Humble/Fortress 이미지로 실행했다. 총 33회 시도 중 유효 23회와 계측 무효 10회가 있었다. 유효 23회 중 수정 전 비교 6회(첫 기준·차단 5회와 첫 fleet 1회)를 보존했고, 17개 조건별 최종 유효 시행을 한 번씩 집계했다. 실제 시각은 주행 로그 기준이며 커밋에는 원 계획의 날짜를 적용했다. [시행별 판정·소스·모델·원시 파일 SHA-256](../../experiments/m5/live-development.json)

[후보별 원시 수치](../../experiments/m5/candidate-replay.json)

명령 전환 회귀시험에서는 센서 누락 시 정지, 지연 시 DWA 전환과 learned 복귀, 목표 취소, 현재 목표의 재계획 이후에만 재출발하는 조건을 확인했다. [운용 상태와 고장 주입 방법](operations.md)

기존 fleet 관리자 코드에 정해진 두 로봇의 위치·속도를 입력한 12초 재생에서도 목표 교체를 확인했다. 관리자는 뒤쪽 `amr2`에만 3.4초에 대기 위치를 발행했고, 앞쪽 로봇이 이동한 뒤 7.2초에 원래 목표를 다시 발행했다. 실제 `fleet` 시험에서는 관리자의 재발행과 후행 로봇의 실측 변위를 함께 대조했다. [관리자 발행 이력](../../experiments/m5/fleet-manager-replay.json)

## 첫 4m 주행에서 확인한 도착 오차

`f857815`로 실행한 여섯 시행 중 다섯 시행에서 전 구간 무접촉이 확인됐다. seed 31 차단은 경로 시간 초과 시점의 접촉 계측이 불완전했다. 아래 오차는 각 시행 종료 시점의 Gazebo 위치와 목표 사이 거리다. 기호 ✓는 실제 이동, 0.4초 이상 정지, 장애물 제거, 제거 후 0.25m 이상 재전진을 시간 순서대로 모두 관측했다는 뜻이다.

| 학습 seed | 기준 주행 | 일시 차단 주행 | 차단 전후 동작 |
|---:|---|---|---|
| 7 | `TIMEOUT`, 15.510m | `ARRIVED`, 0.355m | 이동·제거·재전진 관측, 정지 미관측 |
| 19 | `ARRIVED`, 0.436m | `TIMEOUT`, 2.551m | ✓ |
| 31 | `ARRIVED`, 0.299m | `PATH_TIMEOUT`, 4.178m | 이동·제거·재전진 관측, 정지 미관측 |

세 `ARRIVED` 모두 실제 오차가 0.25m를 넘었다. 기존 운용 제어기는 추정 위치가 목표의 0.4m 안에 들면 도착을 선언했다. `751c220`에서 운용 제어기의 도착 반경을 0.25m로 줄였다. 실제 위치에 대한 독립 판정 기준은 모든 시행에 동일하게 적용했다. seed 7 기준 주행은 목표에 가장 가까웠을 때도 0.511m 떨어졌고, 목표를 지나 계속 전진했다. 이 실패에는 조기 도착 선언과 다른 궤적 추종 문제가 있다.

## 고장 복구와 두 로봇

세 후보 모두 주행 중 스캔 누락에 정지했고, 스캔을 복구하자 다시 움직였다. 35ms 추론 지연 주입 후에는 DWA 주행, 지연 해제 후에는 learned 주행, 목표 취소 후에는 무접촉 정지가 관측됐다. 최종 고장 시험에서 정지 지속시간은 스캔 누락 시 세 후보 모두 0.352초였다. 새 목표에서는 seed 31만 실제 오차 0.222m로 도착했다. seed 7·19는 각각 16.054m·16.133m 떨어진 곳에서 시간 초과됐다.

개별 제어 시험에서는 한 대가 멈춘 1초 동안 다른 한 대가 0.379m 이동했고 첫 로봇도 재출발했다. fleet 시험에서는 최초 재개 시간 초과를 보존했다. 동일 목적지 재발행 시 스캔 이력을 유지하도록 수정한 뒤 후행 로봇은 대기 위치를 유지하고 원래 목적지로 0.253m 전진했다. 최소 간격은 1.600m였고 두 로봇의 모든 수락 목표에 대해 발행자를 확인했다. [대기·재개 전후 상세](pair.md)

## 실행과 결과 확인

맥의 Docker Desktop을 켜고 저장소 루트에서 실행한다. M2·M3에서 사용한 CPU 이미지 `opticore-m2-local:humble-fortress`, M2 파일 묶음, M4 후보 번들 3개가 필요하다. 현재 커밋을 새 컨테이너에서 빌드하고 두 접촉 계측 시험을 통과한 다음 주행을 시작한다.

```bash
bash scripts/m5/run_local.sh paired
```

전체 17회는 `bash scripts/m5/run_local.sh all`로 실행한다. 위 표의 이름을 주면 해당 묶음만 실행한다. 계측 무효 시행 하나를 재실행할 때는 예를 들어 `M5_SEED=31 bash scripts/m5/run_local.sh sequence`를 쓴다. 기준·차단도 각각 `baseline`과 `blockage`로 지정할 수 있다. 위치를 바꾸려면 `M5_PILOT_KIT`에 M2 파일 경로, `M5_RUNS`에 세 후보 디렉터리의 상위 경로를 지정한다. `fleet`와 `all`에는 고정한 `amr_fleet` 패키지도 필요하다. 로컬에 준비된 사본을 사용하거나 `M5_UPSTREAM_REPO`에 `opticore-amr` 체크아웃을 지정할 수 있다. 실행기는 커밋 `e8c9197`에서 해당 패키지를 읽는다.

실행할 때 출력한 `Results` 디렉터리에서 `session.log`로 빌드·기동을, `trials/development/summary.json`으로 시행별 결과를 확인한다. `suite_verdict`는 진행 중 `running`, 전체 통과 `passed`, 측정된 실패 `failed`, 유효한 증거 누락 `invalid`다. 완료 시 종료 코드는 각각 통과 0, 측정된 실패 3, 증거 누락 1이다. 원인 분석을 위해 각 시행의 원시 기록과 실제 시작·종료 시각을 보존한다.

Humble·Fortress가 설치된 리눅스에서는 같은 진입점을 사용할 수 있다. 결과 경로에는 아직 존재하지 않는 디렉터리를 지정한다.

```bash
xvfb-run -a bash scripts/m5/run_on_humble.sh "$UPSTREAM" "$CANDIDATES" "$NEW_RESULTS" paired
```

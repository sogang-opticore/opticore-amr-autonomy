# 창고 주행 비교 구성

원본은 `opticore-amr`의 `e8c9197ac2801c2770c83a7ee696b2b992d473b8`이다. 단일 AMR에서 같은 창고·차체·위치추정·A* 경로·동적 레이어를 사용하는 두 구성을 먼저 비교한다. 향후 학습 제어기의 성능을 분리해 해석하려면 명령 중계가 기존 주행에 미치는 영향부터 측정해야 한다.

| 구성 | 주행 명령 | A* 재계획 입력 | 용도 |
|---|---|---|---|
| B0 | 원본 hybrid `dwa_node`가 로봇의 최종 속도를 발행 | 원본 DWA 상태와 동적 장애물 레이어 | 기존 창고 시스템에서 대표 문제 재현 |
| B1 (M2 어댑터) | 같은 DWA의 후보를 받아 중계기가 최종 속도를 발행 | 같은 동적 레이어와 중계된 유효 상태 | 중계·정지·timeout 도입으로 생기는 회귀 검출 |
| learned (후속 단계) | 정책이 속도를 제안하고 같은 실행 계층이 최종 명령 발행 | 버전을 고정한 공통 인지·상태 계약 | B1과의 차이에서 학습 기여 분석 |

## 연결 경계

원본 `ros2_ws/src/amr_navigation/amr_navigation/dwa_node.py`는 정상 상태에서 Pure Pursuit와 적응 속도 제어를 실행한다. 같은 프로세스가 LiDAR와 지도에서 동적 레이어도 생성한다. `astar_node.py`는 이 레이어·goal·유효 주행 상태를 구독해 경로를 갱신한다. DWA를 통째로 종료하면 A* 입력까지 사라진다. M2에서는 DWA를 유지하고 출력 경계에서 명령과 상태만 분리한다.

각 모드에서 한 로봇의 최종 `cmd_vel` 발행자는 하나여야 한다. B1이 정지를 선택하면 이전 속도를 재사용하지 않는다. 위치추정, 플러그인 접촉 데이터와 명령의 시간축을 보관한다. Gazebo ground truth는 평가 전용이다. 센서·위치 입력이 불량하거나 플래너가 유효한 경로를 받지 못한 시행은 인지/위치/상위 경로/실행 인프라 원인으로 분류한다. 원본 결함을 수정할 때는 원본 SHA와 수정 SHA의 개발용 짝 비교를 남긴다.

## 비교할 때 고정할 것

1. 소스와 빌드, 지도, 차체, 센서, 로봇 이름, 시작 위치와 방향, 임무, 목표 시각, 장애물의 배치·궤적·시계 및 제한시간.
2. 각 시행마다 새 시뮬레이션을 시작하고 TF·지도·위치·접촉 데이터의 준비 상태와 명령 발행자 수를 확인한다. 비교 순서를 교대하고 실행 순서를 로그에 남긴다.
3. 같은 임무·반복 번호로 B0/B1의 완주·접촉·정지/timeout·실패 원인을 대조한다. 둘 다 성공한 쌍에 대해서만 운송시간·이동거리를 따로 비교한다. 한쪽이 실패한 쌍도 전체 임무 성공률의 분모에 남긴다.
4. M2의 어댑터와 이후 제어기의 지원 레이어 구현/구성이 달라지면 새 B1 기준선을 측정한다. 현재 단계의 데이터만으로 학습형 제어기의 성능을 주장할 수 없다.
